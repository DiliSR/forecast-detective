Forecast Detective

Pick any hour from July to December 2014 and the system explains the day-ahead electricity-load forecast of LightGBM, an LSTM, or both. Ask which model to use for a period or a kind of hour and a planner compares them. Every answer is a short text in which every number is checked against computed evidence.

Evidence pack

The writer never sees raw explainer output. It gets up to seven short blocks built by code. Each tag is a citation the writer must use, so any claim points back to exactly one block.

TagWhat the block holdsComes from
[E:forecast]The target hour, the actual load, each model's forecast with its error in kWh and %, and the gap between the two modelsModels and actual load
[E:shap]LightGBM: the six largest contributions in kWh, each with the input value. They add up to the forecastSHAP
[E:lime]LightGBM: the six largest local weights. These are weights, not contributions, and the writer is told to say soLIME
[E:ig]LSTM: the contribution of each input feature, listing only those that move the forecastIntegrated Gradients
[E:timeshap]LSTM: contributions by feature and by past hourTimeSHAP
[E:flags]The disagreement checks that fired, in full, and the names of those that passedSeven disagreement checks
[E:accuracy]Test-period RMSE for this kind of hour: overall, by day type, by part of dayAccuracy slices
  • Trimmed. The raw explanation is about 370 KB. The pack keeps the six largest rows of each explainer and drops inputs that contribute about 0 kWh.
  • Pre-computed. Errors, gaps and percentages are calculated by code and written the way they must be quoted. The writer never does arithmetic, so a number that is not in the pack is a red flag.
  • Per model. Asking about one model builds only that model's blocks and flags, so the other model cannot leak into the text.

Retrieval (RAG)

The explainers say what drove a forecast. Retrieval adds the background that interprets those numbers, such as how to read SHAP or why Christmas Eve behaves like a holiday, together with a source to cite. It supplies no numbers about the forecast.

Where RAG is used

  • Writer prompt. The retrieved passages are added to the prompt as a SOURCES block. Rule 5 lets the writer give a real-world reason only if a source states it, phrased as “according to [S#]”.
  • Checker. A cited [S#] must exist. A sentence that states a cause without a source gets the “Cause without source” caution.
  • The app. Details → Sources lists every passage with its citation and distance. The sidebar can switch the knowledge base off, which runs the writer without sources so the two can be compared.

What gets searched

WhenQuery sent to the index
The hour is on 25 DecemberChristmas Day 25 December major holiday, whole-day load falls by about 40 percent

Always, when LightGBM is explainedSHAP values add up to the forecast minus the expected value, the average model output

  • Why rules, not an LLM. Rule-based queries are repeatable, free and testable, and each carries the reason it was sent.
  • The 0.58 cut-off sits in a measured gap: the best match for on-topic test queries was at most 0.55 away, and for off-topic ones at least 0.62. Weak matches are dropped instead of cited.
  • Known weakness. Retrieval can confuse near-identical calendar sections. Adding keyword search next to the embeddings would help.

Planner

Explanations answer “why was this hour off?”. The planner answers “which model should I use, and where?”. Code makes the decision with a statistical test. The writer only gives the reasons, and cannot change the decision.

Verdicts

VerdictRuleWhat the app does
ClearThe whole 95% interval is above 0, and the RMSE gap is at least 3%Green box: “Use LightGBM for …”
No clear differenceThe gap could be luck, or is too small to matterBlue box: “No clear winner for …”
Too few daysFewer than 5 distinct days. No interval is computedAmber box: “Too few days to separate the models”

  • The explanations enter through the worst hours. A model that missed on 25 December because it leaned on last week's load is a different risk from one that missed for no visible reason.
  • The decision does not depend on the LLM. Switching the writer's model, or the knowledge base, changes the wording of the reasoning and never the headline.
  • Known gap. A writer can still overclaim in a way code cannot see, such as “consistently better across hour types” when seven of eight kinds of hour show no clear difference. The manual review set is for that.

Checker

Plain code reads the writer's text and tests it against the evidence and the sources. No LLM is involved, so the result is exact and free.

CheckRuleIf it fails
Citations existEvery [E:…] and [S#] must be one that was provided. A made-up tag such as [E:made_up] is caughtText fails
Numbers matchA number must appear in a block cited in the same sentence, else in the same paragraph, else anywhere in the evidence. It is compared at the precision written, so 14.6% may be written 15%Text fails
Flags are citedIf any disagreement check fired, the text must cite [E:flags]Text fails
Cause has a sourceA sentence with “because”, “due to” or “the main reason” needs an [S#]. Attributions describe the model, not the real worldCaution only
Number without citationA sentence with a number and no citation is reportedReport only
  • One retry. A failed text goes back to the writer with a list of exactly what failed, including the block where a misquoted number really lives. A second failure is shown with a red badge, never hidden.
  • Planner texts face two more rules: over 110 words, or words that judge a sample (“substantial”, “solid”), send the text back once.
  • Ignored as claims. Feature names (such as the 168 in load_lag_168h), clock times, dates and years are not treated as numbers to verify.
  • What it cannot see. Swapped model names, muddled reasoning that cites a real source, and a missing top driver. These need a person, which is why the manual review set is planned.

Design rules

The agent chooses, code computes

The chat agent resolves the date, hour and model. It never writes an explanation or states a number. explain_hour returns the checked text untouched. The planner works the same way: which model wins is computed, and the writer only explains.

Every number can be traced

A number must appear in an evidence block cited in the same sentence. Unknown citations fail, and a cause with no source gets a caution. A failed check shows as a red badge, never hidden.

Bounded and honest about range

At most 8 agent steps and 3 hours per request. Dates before July 2014 are refused, because the models trained on them and an explanation would describe a memorised fit.
